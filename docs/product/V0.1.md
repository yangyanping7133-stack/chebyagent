# ChebyCodex Mobile V0.1

Status: confirmed product frame
Date: 2026-07-19

## Problem

用户已有一台位于 Turkey 的独立 Codex 容器，但缺少适合手机长期使用的入口。Codex CLI 的多 Thread、流式执行和工具过程不能简单压缩成单一聊天窗口；同时，直接把 app-server 暴露到公网也不安全。

## Primary User

一位拥有自己的远端 Codex 容器、希望随时从手机继续工作且能看懂执行过程的个人用户。V0.1 采用一部手机与一个容器一对一配对。

## Core Journey

1. 用户打开 App，直接进入上次活跃的 Codex 会话。
2. 用户发送文字或附件，App 将其作为当前 Thread 的新 Turn。
3. Codex 的回复、执行进度、证据、确认请求和最终结果以可持续更新的富消息呈现。
4. 用户可以新建、切换、继续、重命名、归档或删除会话。
5. 网络中断后 App 能恢复当前会话和未完成 Turn，而不是制造重复消息。

## In Scope

- Android/HarmonyOS 原生 App
- 单机器人主入口和最近会话默认恢复
- Codex Thread 一对一会话映射
- 会话新建、列表、切换、继续、重命名、归档和删除
- 文字、图片和文件输入的可扩展入口
- 通用富消息：文本、Markdown、进度、状态、证据、图片、对比、确认、动作和交接
- 流式事件、断线重连、幂等发送和失败重试
- 手机与专属远端容器安全配对
- 真机安装、视觉、会话、网络异常和安全边界测试

## Out of Scope

- 多租户 SaaS
- 同一手机同时控制多个 Codex 容器
- 把租房、地图或任何单一业务写死进客户端
- 公网直接暴露 Codex app-server
- V0.1 内实现 iOS 客户端
- 未经确认执行支付、发送消息、发布、删除远端数据等敏感动作

## Product Signature

同一张任务卡随执行状态原地演进，并用“执行交接轨道”表达 Codex 在文件、网页、手机 App 或其他工具之间的推进过程。它应当像一个活的工作面板，而不是不断刷新的日志气泡。

## Acceptance Criteria

- 冷启动默认恢复上次活跃 Thread。
- 新建两个 Thread 后可来回切换，历史内容与远端 Thread 保持一致。
- 重新进入旧 Thread 后，新消息作为该 Thread 的新 Turn，而不是创建隐藏会话。
- 一个进行中的富消息可以通过事件补丁更新状态、步骤、证据和结果。
- 未知富消息类型安全降级为可读文本，不导致会话崩溃。
- 飞行模式/断网/恢复场景不重复提交用户消息，能清楚显示可重试状态。
- 配对密钥不写入日志，不在 UI 暴露原始 app-server 地址、Thread ID 或调试 JSON。
- JUY-AL00 真机完成安装、启动、会话管理、富消息、重连和基础安全回归，并生成可审计证据。

## Safety Boundary

- 网关只向已配对设备开放最小 API；所有写请求带幂等键。
- 敏感副作用必须显示明确确认卡，默认拒绝或等待用户操作。
- 客户端使用系统安全存储保存配对凭据。
- 删除会话前二次确认，并区分可恢复归档与永久删除。
